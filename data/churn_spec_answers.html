Store Activity Dashboard — Design Q&A

Answers to open specification questions from churn_final.docx

Jatak / Coop May 28, 2026 3 sections · 5 questions
Section 1

KPI Summary Cards

Top-level snapshot for the selected date range and chain filter: Butikker med aktivitet, JA TAK-AKTIVE, ANDEN AKTIVITET, TIL OPFØLGNING, and a footer strip with totals / new / exited stores.
1
Should TIL OPFØLGNING include stores that have an HQ push but no self-check, or only stores with zero activity of any kind?
Decision
TIL OPFØLGNING = zero activity of any kind only.

Stores that received an HQ push are already being reached by headquarters — they are not truly dark, just passive. They belong in the ANDEN AKTIVITET card and are flagged as HK-opslag in Section 3.

Mixing them into TIL OPFØLGNING inflates the follow-up number and sends sales teams after stores that HQ is already touching. Keep the two signals clean: ANDEN AKTIVITET = HQ reach, TIL OPFØLGNING = truly unreachable.

Current data reference: 52 stores have HQ push / no self-check; 26 stores have zero activity of any kind. The distinction matters operationally.

2
If a brand-new store does its first self-check in this period, should it count in the main active total or only in the new stores footer strip?
Decision
Count in both — main active total AND the new-stores footer strip.

A store that performs a self-check is an active store, regardless of history. Excluding it from JA TAK-AKTIVE would artificially depress the activity rate.

The footer strip provides the additive context (growth signal) without replacing the primary KPI. New stores should never be subtracted from the headline numbers.

Note: There are currently only 3 brand-new stores in 2026 with no 2025 history — a low number with negligible statistical impact either way, but the principle should be codified consistently.
Section 2

Chain Breakdown Table

No open questions. The agreed logic: TOTAL AKTIVE = EGNE OPSLAG ∪ VIA HK (deduplicated). TIL OPFØLGNING per chain = registered stores with zero self-check and zero HQ push. DÆKNING = total_with_activity ÷ total_registered × 100, sorted descending.
Section 3

Inactive Store Detail List

Shows only stores with a self-check history before the window but silent within it. Status badges: HK-opslag Pause Lukket
1
Inactivity is currently tied to the selected date range — a store silent for just one week appears here. Should a fixed threshold (e.g. 3 or 6 months) be used instead?
Decision
Yes — use a 3-month minimum inactivity threshold to appear in Section 3.

The date range selector controls the analysis window, but Section 3 should only surface stores that have been silent for at least 3 months up to the selected end date. A store that skipped a single week during a campaign break is operational noise, not churn.

3 months aligns with Coop's operational cadence and is a practical threshold for meaningful sales outreach. A 6-month mark can be used as a secondary visual signal (e.g. darker status badge colour) to indicate deeper concern without changing the core filter.

Suggested implementation: filter MÅNEDER_INAKTIV >= 3 in the query. Stores below this threshold are excluded from Section 3 entirely.

2
For the Pause status, should we check inactivity only within the date range or look at all-time activity? The HIST. OPSLAG column hints that past value matters.
Decision
Split approach: badge from date range; MÅNEDER INAKTIV from all-time last check.

The Pause badge is assigned based on the selected date window (no self-check within that period). This keeps badge logic consistent with the rest of the dashboard filters.

However, MÅNEDER INAKTIV must always be calculated from the store's actual seneste_opslag date — not from the start of the selected window. This means: even if you select a 1-month window, you will still see that a store has been silent for 14 months in total.

This gives sales teams the correct prioritisation signal: high HIST. OPSLAG + long MÅNEDER INAKTIV = highest win-back priority, regardless of which window is selected.

3
A Lukket store is flagged purely because it is missing from the current store registry. If it still received an HQ push in the period, should it stay Lukket or be reclassified?
Decision
Reclassify to HK-opslag if the store received an HQ push in the period.

An HQ push is an implicit signal that headquarters considers the store operational. Marking it Lukket at the same time creates a contradiction and risks removing it from the sales follow-up list while HQ is still actively targeting it.

The registry may simply lag behind operational reality. Status resolution priority should be:

In registry? HQ push in period? Self-check in period? Status
NoYesNoHK-opslag
NoNoNoLukket
YesYesNoHK-opslag
YesNoNoPause

This ensures Lukket is reserved for stores with truly no signal of any kind — not even an HQ content push.
